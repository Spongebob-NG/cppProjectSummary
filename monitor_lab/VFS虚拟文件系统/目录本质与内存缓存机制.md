## 目录本质与 Dentry 内存缓存机制

在 Linux 文件系统设计中，**“目录本质也是一个文件”**。理解路径解析的性能关键，在于厘清“磁盘上的持久化目录数据”与“内存中动态构建的 `struct dentry`”之间的协作与转换。



## 磁盘视角：目录文件到底存了什么？

目录与普通文件在磁盘底层的数据结构完全一致：



- **目录的 Inode**：其文件类型标记为目录（`S_IFDIR`），记录该目录的权限、大小，以及分配给它的**磁盘数据块指针**。
- **目录的数据块（Data Block）**：普通文件的数据块存文件内容（如文本、二进制），而**目录的数据块存的是一张紧凑的映射表**。

以 Ext4 为例，目录数据块内部包含若干紧凑的记录项（`ext4_dir_entry_2`）：



| **字段**    | **大小** | **含义**                                   |
| ----------- | -------- | ------------------------------------------ |
| `inode`     | 4 字节   | 该文件对应的 Inode 编号                    |
| `rec_len`   | 2 字节   | 当前目录项总长度（用于快速跳到下一项）     |
| `name_len`  | 1 字节   | 文件名实际字符长度                         |
| `file_type` | 1 字节   | 文件类型（普通文件、目录、套接字等）       |
| `name`      | 变长     | 文件名字符串（如 `main.cpp`，无结尾 `\0`） |

> **关键认知**：磁盘上的目录数据是扁平、紧凑的字节流记录，**磁盘上根本没有指向父子节点的指针，也没有树状拓扑**。

## 内存视角：为什么需要 `struct dentry` 与 dcache？

如果每次解析路径都要去读磁盘数据块，系统会因频繁的磁盘 I/O 陷入停滞。内核在内存中引入 `struct dentry` 与 **dcache（目录项缓存）** 来解决这一问题：



1. **树状拓扑化**：`struct dentry` 内嵌 `d_parent`（指向父目录）、`d_subdirs`（子目录链表）等指针，在内存中动态拼接出一棵真正的**目录树**。
2. **极速哈希查找**：内核维护全局散列表 `dentry_hashtable`。查找路径时直接计算哈希，将 $O(N)$ 的磁盘遍历降低为近乎 $O(1)$ 的内存哈希查找。
3. **负目录项机制（Negative Dentry）**：若访问一个不存在的文件，内核同样会生成一个 `d_inode == nullptr` 的 dentry 保留一段时间，防止恶意穿透访问不存在路径引发持续读盘。

## 路径解析全流程：从按需加载到 LRU 淘汰

当进程发起 `open("/home/user/log.txt", O_RDONLY)` 时，内核的完整执行状态流转如下：



```
用户发起 open("/home/user/log.txt")
  │
  ├── 1. 获取根目录 "/" 的 dentry（常驻内存）
  │
  ├── 2. 查找分量 "home"
  │     ├── 先查 dcache 哈希表
  │     ├── [命中] 直接拿到 home 的 dentry
  │     └── [未命中] 触发磁盘 I/O：
  │           ├── 读取 "/" 的数据块
  │           ├── 遍历找到 "home" 及其 inode 号
  │           └── 在内存动态实例化 struct dentry("home")，挂入 dcache
  │
  ├── 3. 沿链逐级向下重复步骤 2（惰性解析 "user" -> "log.txt"）
  │
  └── 4. 找到目标文件的 Inode，分配并返回 struct file 给进程
```

### 核心运作特性

- **按需惰性加载（Lazy Loading）**：

  开机或挂载时，内核绝不全盘预加载目录。只有程序实际访问某一层路径时，内核才会触发该层目录数据块的磁盘 I/O，并实时在 slab 缓存中分配生成对应的 `struct dentry`。

- **引用计数与 LRU 动态淘汰**：

  - **活跃态（In-use）**：有进程正打开该路径下的文件，`dentry->d_lockref.count > 0`，内核严禁释放。
  - **非活跃态（Unused/Cached）**：文件被关闭，引用计数归 0，该 dentry 不会立即销毁，而是挂入全局 **LRU（最近最少使用）双向链表**。
  - **内存回收（Reclaim）**：当系统可用内存紧张触发内核内存回收（`kswapd` 或直接内存回收）时，内核顺着 LRU 链表将长期未使用的 `struct dentry` 及其关联的非脏 inode 从内存释放（`kfree`）。未来若再次访问，只需按需重新读盘构建即可。

## 面试高频问题与标准答题提纲

### Q1: 目录项到底存在哪里？断电会丢失吗？

- **答题核心**：严格区分**物理存储**与**内核结构**。
- **结构划分**：
  - 持久化保存在磁盘上的是**目录文件的数据块**（存有文件名与 Inode 号的映射表），断电不会丢失。
  - 内核源码里的 `struct dentry` 是**纯内存数据结构**，由内核在解析路径时将磁盘数据块内容反序列化生成。
- **生命周期**：`struct dentry` 由 slab 分配器在 RAM 中分配，关机自然消失，内存不足时内核也会主动回收，因为磁盘上有原始记录作为重建依据。

### Q2: 系统在什么情况下会发生针对目录的磁盘 I/O？

- **场景 1：冷启动 / 首次访问**：目标路径各级目录从未被访问过，dcache 未命中，必须读盘。
- **场景 2：内存压力回收后再次访问**：该路径此前被访问过，但因系统物理内存告急，内核通过 LRU 机制回收了该 dentry，再次访问需重新触发 I/O。
- **场景 3：显式清理缓存**：外部运维或测试脚本执行了 `echo 2 > /proc/sys/vm/drop_caches`（释放 dentry 和 inode 缓存），后续访问会强制穿透到底层存储。
- **场景 4：目录写操作（新建/删除/重命名）**：调用 `mkdir`、`touch`、`unlink`、`rename` 时，不仅要修改内存中的 dentry，还必须将变更写入该目录对应磁盘数据块的脏页中（最终回写刷盘）。
