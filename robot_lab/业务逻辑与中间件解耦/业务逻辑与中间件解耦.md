# 软件架构精要：机器人与自动驾驶中的“业务逻辑与中间件解耦”

## 1. 核心定义：什么是“解耦”？

在软件工程中，“解耦（Decoupling）”的本质是**切断组件之间的隐式绑定与生存依赖，使其互不相欠、各司其职、随时可换**。



- **强耦合（Coupled）**：将按键检测与 USB 数据线焊死的一体式键盘。数据线破损或需要换插 Type-C 时，整个键盘必须报废。
- **解耦（Decoupled）**：键线分离的客制化键盘。键盘主体只负责计算哪个键被按下（业务逻辑），机身只留通用插槽；传输通道可任意换为 USB 线、Type-C、蓝牙或 2.4G 无线模块（通信基础设施）。

### 辨析：“良性内部依赖” vs “恶性外部依赖”

| **依赖类别**                     | **代表元素**                                                 | **特征与代价**                                               |
| -------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **良性依赖（内部数据定义）**     | 原生类型、POD 结构体（`struct`）、纯枚举（`enum class`）     | **纯内存数据表达**。仅依赖 C++ 标准语法，不调用系统 API、不发起网络通信、无硬件依赖。在任何没有安装 ROS 2 的裸机或嵌入式环境均可毫秒级编译运行。 |
| **恶性外部依赖（环境与副作用）** | ROS 2 句柄、DDS 通信协议栈、全局变量/单例、系统时钟、硬件驱动、多线程锁 | **运行环境绑定**。脱离特定操作系统运行时、通信网络或物理实体便无法生存。测试时必须拉起庞大依赖链，极易引发段错误（Segmentation Fault）或超时阻塞。 |

## 2. 设计模式：“函数式核心，命令式外壳”（Functional Core, Imperfect Shell）

该架构（工业界更常称为 **计算与 IO 分离 / 决策与执行分层 / 薄包装模式**）将系统边界划分为两个职责截然相反的层级：



Plaintext

```
[ 外部世界 / ROS 2 节点 (命令式外壳) ]
       │
       │ 1. 抓取当前节点状态并填入纯数据结构
       ▼
┌──────────────────────────────────────────────┐
│  robot_tasks::PlanXxx(...) (函数式核心/纯大脑) │
│  - 纯数学与逻辑裁决，无副作用                │
│  - 输入: const RobotState&                   │
│  - 输出: Decision 结构体                     │
└──────────────────────────────────────────────┘
       │
       │ 2. 返回明确的决策指令
       ▼
[ 外部世界 / ROS 2 节点 (命令式外壳) ]
       │
       │ 3. ApplyXxxDecision(): 执行发包、底盘制动、状态赋值
       ▼
[ 物理硬件 / 网络 DDS 传输 ]
```

### 标准落地三步法

1. **收集状态（State Extraction）**：外壳（ROS 2 节点回调）从成员变量、参数服务器提取需要参与决策的情报，压入纯数据结构体（如 `RobotState`）。
2. **纯函数裁决（Pure Decision）**：调用 `robot_tasks::PlanXxx(state)`。纯函数只做逻辑分支计算，输出纯数据结构体（如 `Decision`）。**内部严禁调用任何通信接口、严禁写全局变量、严禁阻塞等待**。
3. **执行与应用（Effect Application）**：外壳调用 `ApplyXxxDecision(decision)`，根据裁决结果按部就班地发 Topic、调 Service、修改成员变量或向底层控制器写指令。

## 3. 为什么必须解耦？（四大工程必要性）

### ① 零 Mock（Zero-Mock）的亚毫秒级单元测试

- **传统面向对象的痛点**：若要避开真实环境，必须编写抽象接口类，再利用 Google Mock（`gmock`）继承并伪造 `MockPublisher`，编写繁重的 `EXPECT_CALL(...)`。不仅编译极慢，还存在虚函数动态绑定的性能损耗。
- **解耦后的优势**：纯函数仅依赖基本数据类型。在 Google Test 中无需初始化 ROS 2 节点（无需 `rclcpp::init()`），无需创建线程，直接在栈上构造一个 `RobotState` 传给函数，直接断言返回的 `Decision`。几百条测试用例可在几十毫秒内全部跑完。

### ② 确定性与故障 100% 精确复现（Determinism & Reproducibility）

- 机器人现场出现逻辑诡异的偶发 Bug 时，传统混合代码难以排查（多线程时序、网络丢包抖动相互交织）。
- 在解耦架构下，只要在决策入口将当时的 `RobotState` 序列化打印或落盘，在本地开发机上反序列化后扔进核心函数，**单步调试即可 100% 复现现场裁决路径**，彻底告别“现场偶现、本地无法复现”。

### ③ 业务核心资产跨平台零成本迁移（Portability）

- 自动驾驶与机器人领域中间件演进极快（ROS 1 $\to$ ROS 2 $\to$ CyberRT / Iceoryx / 自研微内核通信）。
- 若业务判断与 `rclcpp` 深度纠缠，框架升级意味着全盘重写重测；解耦后，`robot_tasks` 纯逻辑代码是纯粹的 C++ 静态库资产，更换中间件仅需重新写一层不到百行的外壳适配器（Thin Wrapper）。

### ④ 线程安全与并发复杂度降低（Thread Safety）

- 纯函数不依赖也不改变任何外部静态或类内变量，满足**函数可重入性（Reentrant）**。
- 在多线程执行器（`MultiThreadedExecutor`）并发调度下，纯计算逻辑天然无数据竞争（Data Race），不需要加互斥锁（`std::mutex`），杜绝死锁隐患。

## 4. 工程重构实战对比

### ❌ 耦合反例：泥潭代码（Anti-Pattern）

C++

```
// 致命缺陷：逻辑、状态、中间件通信强捆绑
void MissionNode::OnCancelCallback(const std::shared_ptr<CancelReq> req,
                                   std::shared_ptr<CancelRes> res) {
    // 隐患 1：隐式读取类成员变量，输入不透明
    if (this->current_status_ == RobotStatus::CARRYING_HAZARD) {
        
        // 隐患 2：强依赖 ROS 2 专属消息协议
        auto warn_msg = std_msgs::msg::String();
        warn_msg.data = "Hazard detected";
        
        // 隐患 3：强依赖 DDS 网络通信，无网络环境直接崩溃或阻塞
        this->alarm_pub_->publish(warn_msg);

        // 隐患 4：就地产生副作用，测试无法单独验证状态流转
        this->current_status_ = RobotStatus::EMERGENCY_STOPPING;
        res->success = false;
    } else {
        this->cmd_vel_pub_->publish(geometry_msgs::msg::Twist());
        this->current_status_ = RobotStatus::IDLE;
        res->success = true;
    }
}
```

### ✔️ 工业级解耦标准实现

#### 模块一：纯计算核心（`robot_tasks.hpp` / `robot_tasks.cpp`）

*无任何 `#include `，仅依赖标准 C++。*



C++

```
#pragma once
#include <string>

namespace robot_tasks {

enum class RobotStatus {
    IDLE,
    NAVIGATING,
    CARRYING_HAZARD,
    EMERGENCY_STOPPING
};

// 输入契约：纯数据输入
struct RobotState {
    RobotStatus status;
    double battery_level;
};

// 输出契约：纯动作描述
struct CancelDecision {
    bool accept;
    bool should_trigger_alarm;
    bool should_stop_motors;
    RobotStatus next_status;
    std::string reason;
};

// 纯函数裁决：确定性逻辑，输入确定则输出必然确定
inline CancelDecision PlanQueuedMissionCancel(const RobotState& state) {
    CancelDecision decision;
    
    if (state.status == RobotStatus::CARRYING_HAZARD) {
        decision.accept = false;
        decision.should_trigger_alarm = true;
        decision.should_stop_motors = false;
        decision.next_status = RobotStatus::EMERGENCY_STOPPING;
        decision.reason = "Cannot cancel: hazard cargo aboard";
    } else if (state.battery_level < 10.0) {
        decision.accept = false;
        decision.should_trigger_alarm = true;
        decision.should_stop_motors = true;
        decision.next_status = RobotStatus::EMERGENCY_STOPPING;
        decision.reason = "Cannot cancel: critically low battery";
    } else {
        decision.accept = true;
        decision.should_trigger_alarm = false;
        decision.should_stop_motors = true;
        decision.next_status = RobotStatus::IDLE;
        decision.reason = "Cancellation approved";
    }
    
    return decision;
}

} // namespace robot_tasks
```

#### 模块二：命令式外壳（`mission_node.cpp`）

*仅负责 ROS 2 数据搬运与执行动作。*



C++

```
#include <rclcpp/rclcpp.hpp>
#include <std_msgs/msg/string.hpp>
#include <geometry_msgs/msg/twist.hpp>
#include "robot_tasks.hpp"

class MissionNode : public rclcpp::Node {
public:
    MissionNode() : Node("mission_node"), current_status_(robot_tasks::RobotStatus::IDLE), battery_level_(100.0) {
        alarm_pub_ = this->create_publisher<std_msgs::msg::String>("alarm", 10);
        cmd_vel_pub_ = this->create_publisher<geometry_msgs::msg::Twist>("cmd_vel", 10);
    }

    // 外壳回调：退化为轻量编排层
    void HandleCancelRequest() {
        // 1. 抽取状态
        robot_tasks::RobotState state{this->current_status_, this->battery_level_};

        // 2. 纯逻辑仲裁
        robot_tasks::CancelDecision decision = robot_tasks::PlanQueuedMissionCancel(state);

        // 3. 执行副作用
        ApplyDecision(decision);
    }

private:
    void ApplyDecision(const robot_tasks::CancelDecision& decision) {
        this->current_status_ = decision.next_status;

        if (decision.should_trigger_alarm) {
            std_msgs::msg::String msg;
            msg.data = decision.reason;
            alarm_pub_->publish(msg);
        }

        if (decision.should_stop_motors) {
            cmd_vel_pub_->publish(geometry_msgs::msg::Twist());
        }
    }

    robot_tasks::RobotStatus current_status_;
    double battery_level_;
    rclcpp::Publisher<std_msgs::msg::String>::SharedPtr alarm_pub_;
    rclcpp::Publisher<geometry_msgs::msg::Twist>::SharedPtr cmd_vel_pub_;
};
```

#### 模块三：超轻量单测（`test_robot_tasks.cpp`）

*不需要依赖 ROS 运行时，几毫秒内验证全部边界条件。*



C++

```
#include <gtest/gtest.h>
#include "robot_tasks.hpp"

TEST(MissionCancelTest, RejectsWhenCarryingHazard) {
    robot_tasks::RobotState input{
        .status = robot_tasks::RobotStatus::CARRYING_HAZARD,
        .battery_level = 85.0
    };

    auto decision = robot_tasks::PlanQueuedMissionCancel(input);

    EXPECT_FALSE(decision.accept);
    EXPECT_TRUE(decision.should_trigger_alarm);
    EXPECT_FALSE(decision.should_stop_motors);
    EXPECT_EQ(decision.next_status, robot_tasks::RobotStatus::EMERGENCY_STOPPING);
}

TEST(MissionCancelTest, RejectsWhenBatteryCritical) {
    robot_tasks::RobotState input{
        .status = robot_tasks::RobotStatus::NAVIGATING,
        .battery_level = 8.5 // 低于 10.0 阈值
    };

    auto decision = robot_tasks::PlanQueuedMissionCancel(input);

    EXPECT_FALSE(decision.accept);
    EXPECT_TRUE(decision.should_trigger_alarm);
    EXPECT_TRUE(decision.should_stop_motors);
    EXPECT_EQ(decision.next_status, robot_tasks::RobotStatus::EMERGENCY_STOPPING);
}

TEST(MissionCancelTest, AcceptsUnderNormalConditions) {
    robot_tasks::RobotState input{
        .status = robot_tasks::RobotStatus::NAVIGATING,
        .battery_level = 50.0
    };

    auto decision = robot_tasks::PlanQueuedMissionCancel(input);

    EXPECT_TRUE(decision.accept);
    EXPECT_FALSE(decision.should_trigger_alarm);
    EXPECT_TRUE(decision.should_stop_motors);
    EXPECT_EQ(decision.next_status, robot_tasks::RobotStatus::IDLE);
}
```

## 5. CMakeLists.txt 的工程化组织架构

解耦必须体现在构建系统的编译目标（Target）隔离上。必须将纯逻辑代码编为一个独立的纯 C++ Target，完全切断其对 `rclcpp` 的链接依赖：



CMake

```
cmake_minimum_required(VERSION 3.16)
project(robot_mission_control LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# -----------------------------------------------------------------------------
# 1. 纯业务逻辑静态库（完全无 ROS 依赖，秒级编译）
# -----------------------------------------------------------------------------
add_library(robot_tasks_core STATIC
    src/robot_tasks.cpp
)
target_include_directories(robot_tasks_core PUBLIC
    include
)

# -----------------------------------------------------------------------------
# 2. 单元测试 Target（仅依赖 GTest 与核心逻辑，脱离 ROS 环境独立运行）
# -----------------------------------------------------------------------------
find_package(GTest REQUIRED)
add_executable(unit_tests
    test/test_robot_tasks.cpp
)
target_link_libraries(unit_tests PRIVATE
    robot_tasks_core
    GTest::gtest
    GTest::gtest_main
)

# -----------------------------------------------------------------------------
# 3. ROS 2 可执行节点（外壳：装配中间件与核心库）
# -----------------------------------------------------------------------------
find_package(ament_cmake REQUIRED)
find_package(rclcpp REQUIRED)
find_package(std_msgs REQUIRED)
find_package(geometry_msgs REQUIRED)

add_executable(mission_node_exec
    src/mission_node.cpp
)
target_link_libraries(mission_node_exec PRIVATE
    robot_tasks_core
)
ament_target_dependencies(mission_node_exec
    rclcpp
    std_msgs
    geometry_msgs
)

install(TARGETS mission_node_exec DESTINATION lib/${PROJECT_NAME})
ament_package()
```

## 6. 面试与工程沟通的标准话术

在智能驾驶或机器人 C++ 软件开发面试中，被问及“如何设计系统架构”**或**“如何做单元测试”时的表达模板：



> “在模块架构设计上，我推崇**业务逻辑与底层基础设施（IO/通信中间件）解耦**的设计模式。
>
> 在 ROS 2 任务控制节点开发中，我杜绝在 Topic 和 Service 回调函数内部直接编织分支判断。相反，我将系统状态和决策动作抽象为独立的纯数据结构（POD），将全部决策逻辑下沉为无副作用、无外部依赖的纯函数（Pure Logic Layer）。
>
> ROS 2 节点仅作为一层薄外壳（Thin Wrapper），只负责数据的收取映射以及决策下发后的执行。
>
> 这种解耦方案为团队带来两大显著工程收益：
>
> 1. **实现零 Mock 的轻量级单元测试**：测试时不拉起任何中间件与仿真环境，以纯数据驱动 GTest，毫秒级达成 100% 的分支覆盖率；
> 2. **提升核心资产的可移植性与确定性**：业务层完全摆脱对 `rclcpp` 接口的依赖，现场定位 Bug 时可通过数据重放实现确定性单步调试，未来若底层切换至 CyberRT 或自研中间件，核心逻辑库可零成本平移。”
